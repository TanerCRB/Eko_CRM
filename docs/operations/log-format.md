# Log format

This file is the **one place** where the form of every container log line of the composition is
written down, so that the IT department reads a fixed form and its monitoring is connected to it
(EKO-1-08). The design is ADR-0005's addendum of 2026-11-02
([ADR-0005](../architecture/decisions/ADR-0005-personal-data.md), *Log settings and line forms of
every service but Keycloak*). A change to a line's form is a change to that addendum, and the
tests read the key sets below from this file.

Every container log is read with `docker compose logs <service>`. No service writes a log file.

## Key sets

One row per line form. A key marked *(optional)* is present only when its condition holds; every
other key is always present, in the order written.

| Line | Keys, in order |
|---|---|
| `app.request` | `ts`, `level`, `process`, `logger`, `event`, `method`, `route`, `status`, `duration_ms`, `correlation_id` |
| `app.error` | `ts`, `level`, `process`, `logger`, `event`, `error`, `at`, `cause` *(optional)*, `correlation_id` *(optional)* |
| `app.message` | `ts`, `level`, `process`, `logger`, `event`, `msg`, `correlation_id` *(optional)* |
| `proxy.access` | `level`, `ts`, `logger`, `msg`, `request.client_ip`, `request.method`, `request.host`, `request.uri`, `duration`, `size`, `status` |
| `proxy.error` | `level`, `ts`, `logger`, `msg`, `request.client_ip`, `request.method`, `request.host`, `request.uri`, `duration`, `status` |

## `backend`, `migrate` and `worker`

Each line is one JSON object on standard error, UTF-8 with every character outside ASCII escaped,
so no value can split or forge a line. Uvicorn's own lines are in the same form.

- `ts`: the log record's creation time, RFC 3339 in UTC with microseconds and `Z`.
- `level`: `INFO`, `WARNING`, `ERROR` or `CRITICAL`.
- `process`: `backend`, `migrate` or `worker`.
- `logger`: the name of the logger that wrote the line.
- `event`: `request`, `error` or `message`, which decides the keys that follow.

### `request`: one line per request `backend` receives

Written once the response has ended or failed, for every path and every status, the container
healthcheck's requests included.

- `method`: `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `TRACE` or `CONNECT`;
  any other method is `OTHER`.
- `route`: the matched route's template (`/api/health`). When no route matched (a 404, a
  trailing-slash redirect), the request's path with each segment written `*`, unless the segment
  is a fixed segment of a route of the application or a lower-case canonical UUID. Cut at 256
  characters. The query string is never written.
- `status`: the response's status code.
- `duration_ms`: from the request's arrival to the end of its response, in milliseconds, measured
  with a monotonic counter.
- `correlation_id`: 32 lower-case hexadecimal digits, generated by `backend` for this request and
  returned to the client in the response header `Eko-Correlation-Id`. No value a client sends is
  ever used or echoed.

```json
{"ts":"2026-11-02T10:15:30.123456Z","level":"INFO","process":"backend","logger":"app.main","event":"request","method":"GET","route":"/api/health","status":200,"duration_ms":3.214,"correlation_id":"4f1c2d0a9b8e7f6a5d4c3b2a19087f6e"}
```

### `error`: an exception, as its type and location only

No line holds an exception's message, arguments, notes or traceback.

- `error`: the exception's module and qualified name (`psycopg.errors.UniqueViolation`). An
  exception group is written as the group's own type.
- `at`: `<module>:<function>:<line>` of the innermost frame of the application's own code
  (`app.data.schema_revision:refuse_unless_servable:212`; under `migrations/`, the file's path,
  `migrations/env.py:run_upgrade:118`), or of the innermost frame when no application frame exists.
- `cause` *(optional)*: the type of its explicit cause, otherwise of the exception it was raised
  while handling. One level only.
- `correlation_id` *(optional)*: when the exception was raised while a request was handled.

An unhandled exception in a request is answered `500` with the body `Internal Server Error` and
writes exactly one such line. An error outside a request writes the line without
`correlation_id`, and the process exits non-zero.

A database error is SQLAlchemy's wrapper in `error` and the driver's type in `cause`; a rule that
looks for a PostgreSQL condition matches `cause`. In the example the request's own code is not
under `app/`, so `at` is the request handling's frame; a query in `app/data/` names that module.

```json
{"ts":"2026-11-02T10:15:31.000001Z","level":"ERROR","process":"backend","logger":"app.main","event":"error","error":"sqlalchemy.exc.IntegrityError","at":"app.main:RequestHandling.__call__:105","cause":"psycopg.errors.UniqueViolation","correlation_id":"0b7d5e3f2a1c4b6d8e9f0a1b2c3d4e5f"}
```

A warning is written in the same form with `level` `WARNING` and `logger` `py.warnings`: `error`
is the warning's category and `at` where it was raised, with no `cause` and none of the warning's
text, so a monitoring rule tells a warning from an error by `level`.

```json
{"ts":"2026-11-02T10:15:32.000002Z","level":"WARNING","process":"backend","logger":"py.warnings","event":"error","error":"builtins.UserWarning","at":"app.api.health:health:38","correlation_id":"0b7d5e3f2a1c4b6d8e9f0a1b2c3d4e5f"}
```

### `message`: any other line

- `msg`: for the application's own loggers (`app`, `app.*`), the message with its values, which
  are only values ADR-0005 allows. For any other logger (uvicorn, Alembic, a library), the
  message's **format string**: its arguments are never written (`Started server process [%d]`).
- `correlation_id` *(optional)*: while a request is handled.

```json
{"ts":"2026-11-02T10:15:29.500000Z","level":"INFO","process":"worker","logger":"app.worker","event":"message","msg":"worker started; no jobs are defined"}
```

Loggers outside `app` write from `WARNING` up, except `uvicorn.error` from `INFO`.

### Two plain-text forms

These are not JSON. They are the message of the process's exit, which the interpreter writes as
the last line before a non-zero exit:

- `configuration error: missing, empty or invalid environment variable(s): <NAMES>`
  (ADR-0004-C10), naming variables only;
- `<process> refused to start: <reason>` and `migrate refused: <reason>` (ADR-0004, addendum of
  2026-10-29), naming revision identifiers only.

## `proxy`

JSON, one object per line, on standard error. Every logger of Caddy uses the same field
restriction, so no request or response header, cookie, remote address or port, protocol, TLS
detail or query string is written. The host name is written once, as `request.host`.

- `ts`: RFC 3339 in UTC with nanoseconds and `Z`.
- `level`, `logger`, `msg`: Caddy's fixed labels (`handled request` for an access line).
- `request.client_ip`: the address the connection came from; a client's `X-Forwarded-For` is not
  trusted.
- `request.uri`: the path, with everything from the first `?` removed.
- `size`: the response body in bytes; `duration`: seconds, as a number.

Each request writes exactly one access line (`proxy.access`), a request `proxy` answers itself
included. A request whose upstream fails (502, 504) also writes at most one error line
(`proxy.error`), whose `msg` is the upstream failure reason. Caddy's start, stop, certificate and
listener lines carry their own keys under the same restriction.

```json
{"level":"info","ts":"2026-11-02T10:15:30.120000000Z","logger":"http.log.access.log0","msg":"handled request","request":{"client_ip":"192.0.2.10","method":"GET","host":"crm.example","uri":"/api/health"},"duration":0.004,"size":15,"status":200}
```

`proxy` carries no correlation identifier: it writes no header value other than the host name.

## `frontend`

`frontend` writes no line per request. Its own lines (start, stop, an error) are Caddy's JSON
under the same field restriction as `proxy`'s.

## `postgres`

Plain text on standard error, one line per message, with the prefix
`<time UTC> [<process id>] <SQLSTATE> ` and, for a session, `<role>@<database> <client address> `
before the level (`log_line_prefix = '%m [%p] %e %q%u@%d %h '`).

- Written: connection events (received, authenticated, authorized, disconnection), the server's
  start, stop, checkpoint and recovery messages, and FATAL and PANIC messages. A connection that
  fails at start-up writes one FATAL line naming the role, database or start-up value the client
  sent (`28P01` for a failed password, `3D000` for an unknown database).
- Never written: a failed statement (no ERROR or WARNING line at all), statement text, bind
  parameters, `DETAIL`, `HINT`, `QUERY` or `CONTEXT` lines.

The settings are `-c` pairs in the `postgres` service's command in `compose.yaml`, and part of the
release.

## `backup`

`backup`'s lines and its one failure line are written down in
[`backup/README.md`](../../backup/README.md), which stays their one place.

## Keycloak

Keycloak's log content is EKO-1-12's and is not described here.

## How long a line is kept

No service declares a log driver or log options, so every container log uses the driver its
host's container runtime is configured with. Each shared host's runtime deletes container log lines
no later than 14 days after they were written (ADR-0005-C6 as restated on 2026-11-02, set up at
EKO-1-08). Developer and CI hosts are not bounded.
